Run it

Open a tab on a laptop or a phone and start. Nothing to install, no account, no server. A server only enters the picture if you want to drive a paid generation API, and that is a limit of browsers rather than of this tool.

Open the toolSee how it works

In your browser, right here

The whole engine is the page: the planner, the image analysis, the fidelity audit, the clip measurements and the final render.

  1. Open the tool

    It is the front page of this site, a static page on GitHub Pages. There is nothing to sign into and nothing to wait for.

  2. Create a project and add your renders

    One to eight images of one project, from Choose photos or dropped onto the page. They are read in the tab and never uploaded anywhere. In a hurry, Start a sample project draws two renders and fills in the brief so you can see the whole pipeline run first.

  3. Name the finishes, state the location, approve the plan

    The plan is deterministic, so the same intake always gives the same shot list and you can predict what a change will do.

  4. Generate, measure, sequence, render

    Out of the box it uses a demo generator that costs nothing and still exercises every gate, so you can take a project all the way to a finished film before deciding whether to spend anything.

On a laptop there is no photo library for a web page to open. A browser can open the file dialog and nothing else, so if your pictures live somewhere a dialog cannot reach, use one of the other two ways in: drag the images onto the page, or copy one anywhere and paste it with Ctrl + V, or ⌘V on a Mac. Both skip the dialog and any filter it applies, which is also how a JPEG with no filename extension gets in.
Everything stays on your machine. Projects, renders, generated stills, clips and films live in this browser’s own storage. No server ever sees them. That is the good news and the catch: clearing site data for the address erases the lot, and another device will not see your projects. Download the film and the stills pack when a project is done, or export the whole project as one ZIP from the project list and import it on any machine.

On a phone

Same address, same tool. Open it on the phone and work from the camera roll.

  1. Open the link and create a project

    No app, no sign-in. The projects live in the phone’s browser.

  2. Choose photos

    That button opens the photo library and takes JPEGs straight from the camera roll, several at once. Take a photo opens the camera instead, which is the one to use on site. The button asks the phone for image/* and nothing more specific, because that is the one value every phone maps to its gallery: a longer list of formats sends some phones to the file manager instead, which is how a gallery button ends up unable to reach the gallery.

  3. Work through the stages by tapping

    The brief is tappable options rather than a wall of dropdowns, the shot plan scrolls sideways inside its own panel, and each clip becomes its own block with its measurements under it.

JPEG, PNG and WebP are read directly. A JPEG is a JPEG whatever produced it: baseline or progressive, colour or greyscale, any chroma subsampling, and with or without a filename extension. The decoder decides, not the type header, because a gallery can hand a browser a perfectly good photo labelled as raw bytes with no name at all. A photo carrying an orientation tag is turned upright on the way in, so a picture taken with the phone held sideways is not a film shot sideways.
Phone photos are handled as phone photos. A twelve-megapixel picture is resampled to 2048 pixels on its long edge as it comes in, because a phone cannot hold a dozen full-size images in canvas memory at once; nothing is cropped and the page says when it has done it. A phone shoots 4:3 and the default film is 16:9, so the first save offers you the ratios that keep most of the frame, one tap each. An iPhone HEIC opens in Safari, which reads the format natively; if another browser refuses it, set Settings › Camera › Formats to “Most Compatible”.
A phone is for shooting, reviewing and approving; render the final film on a laptop. The render defaults to half size on a small screen, because a full 1080p canvas plus several video tracks plus an encoder is more than most phones will hold. Half size is fine to check the cut. When the film is settled, open the same project on a laptop and render it full size. Projects do not travel between devices on their own: export the ZIP from the project list and import it on the other machine.
Leave the screen on while a clip or the film is being written. The tool asks for a wake lock so the screen does not time out, but if you switch apps the picture freezes while the clock keeps running, and the tool throws that render away rather than hand you a frozen film.
Keep the tab in front while video is being written. Clips and the final film are recorded in real time, so a 45-second film takes about 45 seconds. A browser freezes animation in a background tab, which would record a still picture over a running clock, so the tool throws that render away rather than hand you a frozen film. Run it and let it run.

What the browser can and cannot encode

The film is recorded from a canvas, so its format is whatever the browser will encode. Chrome, Edge and Safari on a normal desktop write H.264 in an MP4, which is what a client can drop into a slide deck. Firefox and some builds of Chromium have no H.264 encoder and write VP9 in a WebM, which plays in any browser but not in QuickTime, PowerPoint or most editors.

The tool does not guess at this. It records a fraction of a second, reads the bytes back, and tells you in Settings and on the render page exactly what it produced. A file is never given an .mp4 name for something an MP4 cannot hold.

If you land on WebM and need an MP4, open the film in Chrome, Edge or Safari instead, or run the file through any converter.

If something does not work

The tool is the page, so when it fails it fails in the page, and it says so in the page.

Open the tool and press Check this browser, on the first screen or under Settings. It reports, one line at a time, whether the browser can store projects, decode a JPEG, open a file picker, record video and in what format, play sound and read an exported ZIP. Anything marked in red is the reason. The report copies as plain text, so you can send it on as it is.

If a page ever comes up blank or half-drawn, it says that too rather than sitting there empty: the failure is printed across the top with the same check one tap away.

Using a paid API, and why that alone needs a server

Everything else runs in the page. This one thing genuinely cannot.

A web page can only read a reply from another site when that site marks the reply readable, which is what the CORS rules are. An API that authenticates with a secret key normally refuses, precisely so a key cannot be used from a web page. That is a sensible rule and it is not something this tool can wave away.

So the tool does not pretend. Paste a key under Settings, press Test the key, and it says plainly whether calls from your browser get through. If they do, real generation works from the page with nothing else running. If they do not, nothing is charged, and you can point the base URL at a relay you control that adds the headers. Only use a relay that is yours: anything in between sees your key.

The key lives in this browser. A static page has no server to keep a secret on, so the key is stored in this browser’s storage on this device, never sent anywhere by this page, and never put in the repository. On a shared machine, do not paste one.

The repository also carries the original FastAPI and ffmpeg version of the same engine, for anyone who wants server-side key handling or guaranteed H.264 output. It is not needed to use this tool, and nothing on this site depends on it. The README covers it.
